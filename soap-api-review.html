Technical Writing Case Study

Legacy SOAP API Documentation Review

A retrospective review of a legacy SOAP API specification, focusing on contract consistency, XML examples, data types, and actionable documentation improvements.

Overview

This case study examines technical documentation for a legacy SOAP API associated with a transport infrastructure monitoring system. The review focuses on the clarity and consistency of the available API contract and its illustrative examples.

The work demonstrates a structured documentation review: identifying discrepancies, describing their potential impact, and recommending verification or corrective actions.

Scope of Review

  • SOAP operations and request/response structures.
  • WSDL and XML Schema (XSD) definitions.
  • XML request and response examples.
  • Field data types and optionality.
  • Identifier formats and collection response examples.
  • Consistency between the documented contract and example payloads.

API Operations

Operation Purpose
AddEvent Submit an event to the service.
AddEventEx Submit an extended event payload.
GetKnownCoords Retrieve known coordinate data.
GetKnownStrategies Retrieve known event strategy data.

Operation purposes are summarized from the available specification.

Review Findings

1. Potential Data Type Inconsistency

The documented StrategyId field is declared as xs:dateTime, while an example supplies a GUID-like identifier.

Recommendation: Verify the field type against the authoritative WSDL, XSD, and service implementation. Align the schema and examples once the intended contract is confirmed.

2. Incomplete Collection Example

The GetKnownCoords response example contains an empty array, so it does not demonstrate the structure of a populated response.

Recommendation: Add a representative response with one or more coordinate entries. Explain field names, data types, and cardinality.

3. Unclear Field Optionality

Required and optional fields are not always easy to distinguish between the specification's field tables and schema definitions.

Recommendation: Document requiredness consistently and verify it against minOccurs, nillable, and the relevant schema declarations.

4. Undocumented Return Value Semantics

The AddEvent and AddEventEx examples return strings resembling resource paths or identifiers, but their meaning and format need clarification.

Recommendation: Explain successful return values, provide representative examples, and document SOAP faults or error responses where supported by the contract.

5. Apparent Typographical Error in a Schema Type

One field table contains xs:srting, which appears to be a misspelling of xs:string.

Recommendation: Correct the spelling in the documentation and verify that the field table agrees with the underlying schema.

Documentation Quality Recommendations

  • Use the WSDL and XSD as contract references after verifying their relationship to the implementation.
  • Keep field tables synchronized with schema definitions.
  • Provide realistic request and response examples for each operation.
  • Explain identifier formats, collection structures, optional fields, and error behavior.
  • Distinguish confirmed defects from discrepancies requiring implementation-level verification.
